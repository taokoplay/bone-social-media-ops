# 项目级内容分发与获客渠道分析

## 目标与边界

当运营对象是 App、SaaS 或其他具有站外转化链路的产品时，不把自媒体互动当作最终结果。建立项目级渠道地图，把内容平台、App Store、Apple Ads、官网和产品内数据连接成可复核的获客漏斗，判断内容是否带来正确用户。

本文件负责：

- 识别自媒体之外的发现、承接和转化渠道；
- 将 App Store 作为搜索发现与下载转化渠道纳入项目分析；
- 统一跨渠道时间窗口、数据来源、缺失值和归因表述；
- 使用商店搜索需求辅助内容选题，并用激活、留存或付费验证用户价值；
- 为下一轮内容或承接页实验提出单变量动作。

本文件不负责完整 ASO、广告投放或产品经营分析。关键词池、元数据配置、自然排名监控、Apple Ads 出价与广告组、CPP/PPO、SKAdNetwork/AdAttributionKit 深度实现，以及 CAC、LTV、ROAS 和收入模型，应交给对应的 ASO、投放或产品分析流程。涉及这些问题时，本 Skill 只整理与内容运营有关的接口和证据，不冒充专项能力。

## 渠道角色地图

先按用户旅程定义渠道角色，不把所有平台指标混成一张排行榜：

| 渠道 | 主要角色 | 可回答的问题 | 常见指标示例 |
|---|---|---|---|
| 小红书等内容平台 | 激发兴趣、教育用户、建立信任 | 哪类内容让用户愿意进一步了解？ | 曝光、打开/播放、停留、互动、主页访问 |
| App Store 自然搜索/浏览 | 承接主动需求、产品发现与下载决策 | 用户在找什么，产品页是否承接？ | 商店展示、产品页浏览、首次下载、重新下载、转化率、来源类型 |
| Apple Ads | 付费搜索获客与需求验证 | 哪些搜索意图能通过付费触达并转化？ | 展示、Tap、安装、TTR、转化率、CPA；以官方字段为准 |
| 官网/落地页 | 补充信息、建立信任、跳转商店 | 内容流量是否继续进入下载链路？ | 会话、CTA 点击、商店跳转 |
| App 内分析 | 验证用户是否匹配和产品是否兑现承诺 | 获得的用户是否激活、留存、付费？ | 首次打开、关键行为、D1/D7/D30、试用、订阅、收入 |
| 直接/品牌/不可归因 | 存量认知或归因缺失 | 有多少结果无法安全归给具体内容？ | 品牌词、直接访问、未知来源 |

项目档案只记录实际存在且可核验的渠道。没有数据的渠道标记为 `unknown` 或 `null`，不能为了补全漏斗假设数值。

## 跨渠道漏斗

根据项目实际能力选择漏斗，不要求每个项目都有全部层级：

```text
需求信号
→ 内容/广告/商店曝光
→ 内容消费或产品页访问
→ 官网/商店承接
→ 下载或注册
→ 首次打开
→ 首次关键行为
→ 留存
→ 试用/订阅/成交
```

对“小红书 → App Store → App 内”的常见链路，可表达为：

```text
笔记曝光 → 笔记打开/播放 → 主页或链接访问
→ App Store 产品页访问 → 下载 → 首次打开
→ 首次关键行为 → D1/D7 留存 → 试用/订阅
```

每个箭头都需要真实分母和可比窗口。中间任一层不可得时，保留断点，不跨过未知环节计算转化率或断言瓶颈。

## 指标不可互相冒充

跨渠道展示可以并列，但不得直接混算或排序：

- 小红书浏览/播放不等于 App Store 展示；
- 内容收藏率不等于商店下载转化率；
- Apple Ads Search Popularity 是相对需求信号，不写成精确搜索次数；
- Apple Ads 广告搜索词报告不自动等同于全市场热词榜；
- 商店下载不等于首次打开、激活或留存；
- 账号净增粉、同期下载增长或品牌词增长不自动归因给某篇内容；
- App Store Connect、Apple Ads、产品分析工具中的同名指标也要保留原始定义、时区和来源。

原始数据使用平台官方字段名或在项目契约中建立明确映射；展示层可以使用中文标签，但不能改变语义。

## 数据来源与快照契约

合法来源包括：

- App Store Connect / App Analytics 官方界面、许可接口或用户授权导出；
- Apple Ads 官方界面、许可 API 或用户授权导出；
- 自有产品分析、官网分析与已获授权的数据仓；
- 用户人工提供并核验的静态数据。

每条跨渠道快照至少记录：

```yaml
snapshot_at: "YYYY-MM-DDTHH:mm:ssZ"
channel: "xiaohongshu/app_store/website/apple_ads/in_app/..."
market: "国家或地区；未知为 null"
lifecycle_window: "24h/3-7d/custom"
metric_name: "平台原始或已定义映射字段"
metric_value: null
metric_unit: "count/rate/currency/..."
source: "官方界面/API/授权导出/人工核验"
timezone: "数据口径时区"
attribution_scope: "direct/assisted/correlated/unknown"
notes: "口径、异常或限制"
```

沿用 `performance-data-governance.md` 的原则：快照追加不覆盖，未知与 0 分开，同生命周期比较，缺少分母不计算比率。

## 归因等级

跨渠道分析必须把“归因”和“同期变化”分开：

1. **Direct（直接归因）**：平台或自有链路提供可验证的内容/活动级归因，且时间、目标和去重口径明确。
2. **Assisted（辅助影响）**：有可验证的跳转、优惠码、专属页面或受控实验，能证明参与链路但不能独占功劳。
3. **Correlated（同期相关）**：内容发布与商店访问、品牌搜索或下载同期变化，但缺少用户级或活动级连接；只能称“同期变化/相关信号”。
4. **Unknown（不可归因）**：来源、窗口或分母不足，不分配渠道功劳。

不得把 Correlated 写成 Direct。不能因为某篇内容发布后下载上升，就说该内容“带来这些下载”。先排除版本发布、推荐、广告、节假日、价格和其他同期活动。

## 搜索需求反哺内容

Apple Ads 或商店搜索数据可作为需求情报，而不是自动成为内容标题或 ASO 结论：

```text
官方/授权搜索需求数据
→ 还原用户意图
→ 对照已上线产品能力
→ 排除品牌蹭词、事件词和错误预期
→ 转为内容主题与用户语言
→ 用内容表现、商店承接和下载后价值共同验证
```

筛选至少回答：

1. 用户搜这个词真正想完成什么？
2. 当前产品是否真实解决该需求？
3. 内容标题、封面、正文与商店页是否表达一致？
4. 下载后的首次关键行为与留存是否支持“正确用户”判断？

官方搜索热度只说明存在需求信号，不证明产品应该抢词，也不证明内容会获得流量。

## 分析输出顺序

跨渠道复盘按以下顺序交付：

1. **渠道地图**：每个渠道的角色、数据状态和负责人。
2. **数据健康**：来源、窗口、时区、缺失字段、归因等级和可比性。
3. **分段漏斗**：只展示具有真实分母的层级，明确断点。
4. **渠道内表现**：分别分析内容、商店、广告、官网和 App 内数据。
5. **跨渠道关系**：列出直接归因、辅助影响、同期相关和未知。
6. **用户价值验证**：下载后是否激活、留存或进入有效商业路径。
7. **下一实验**：只改变一个主要变量，写明保持不变项、窗口和停止条件。

## 单变量实验示例

围绕“旅行足迹地图”需求验证时：

- 本轮只改：小红书封面和标题中的用户语言；
- 保持不变：内容结构、CTA、App Store 产品页、产品版本和投放；
- 观察：内容打开、主页/链接访问、商店访问、下载及可得的激活数据；
- 结论：有直接归因才报告内容带来的下载；否则报告同期信号；
- 停止条件：达到约定的可比实验次数、样本仍不足、成本过高或产品承接假设被否定。

若要同时修改 App Store 元数据或产品页，那已是另一项实验，应分轮执行或使用受控实验工具，避免无法判断结果来自内容还是商店承接。

## 自动化边界

可自动化：

- 定期处理官方许可 API、用户授权导出或已落地数据仓；
- 追加快照、检查口径、生成趋势与异常报告；
- 发现数据缺失、归因断点和候选实验。

不可自动化：

- 用无人值守浏览器抓取受限后台或小红书网页；
- 绕过登录、验证码、频控或权限；
- 自动调整 Apple Ads 出价、关键词或预算；
- 自动修改 App Store 元数据、产品页或公开内容；
- 在无直接归因证据时自动分配渠道功劳。
